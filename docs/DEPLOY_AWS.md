# Deploying on AWS

Same shape as [DEPLOY.md](DEPLOY.md): Caddy and the API run in Docker on one EC2 instance; Postgres is RDS **or, after the cutover in "Database" below, a container on the same server**; private files go to S3. The cloud resources are one CloudFormation stack: `deploy/aws/nakama.yaml`.

```
internet -> Caddy (80/443) -> api (uvicorn) -> Postgres 16: RDS (private, SSL)  or  the `db` container
              EC2 t3.small, Elastic IP          S3 bucket via the instance role
```
No SSH: use SSM (`aws ssm start-session --target <instance-id>`). The database password and `SECRET_KEY` are generated by Secrets Manager and read on the instance at deploy time; they never appear in git, chat or EC2 user-data.

## First time
```bash
aws cloudformation create-stack --stack-name nakama --capabilities CAPABILITY_IAM \
  --template-body file://deploy/aws/nakama.yaml \
  --parameters ParameterKey=VpcId,ParameterValue=<vpc> ParameterKey=InstanceSubnetId,ParameterValue=<subnet> \
               ParameterKey=DbSubnetIds,ParameterValue='"<subnet-a>,<subnet-b>"'
aws cloudformation wait stack-create-complete --stack-name nakama
```
Point a DNS A record at the `ApiEip` address (stack outputs show it), then deploy. Without a domain the stack's `ApiUrl` (an `sslip.io` name) works.

## Branches and releases
Features branch off and merge into `main` through pull requests; CI runs there. **`production` is the release branch.** Promote a tested `main` commit to it and the server deploys it within a minute:

```bash
git push origin main:production      # fast-forward; only the owner can push it
```
How it works: the instance runs a systemd timer (`nakama-pull-deploy`) that asks GitHub for the head of `production`. If it changed and `test` and `docker` are green on that exact commit, it fetches it, builds it, runs `alembic upgrade head`, restarts, and waits for the API to be healthy. If the new API never becomes healthy it goes back to the previous release. A commit whose CI failed is skipped until a new commit arrives. No AWS keys live in GitHub, and nothing in GitHub can reach the server: the server asks GitHub (the repo is public, so no credentials are needed). The free plan's policy blocks GitHub-to-AWS OIDC, which is why it is built this way.

Watch it: `aws ssm start-session --target <instance-id>`, then `journalctl -u nakama-pull-deploy -n 50`.
**Roll back:** push a revert commit to `main`, let CI pass, promote it. Migrations must stay additive (see ONBOARDING), so older code keeps working on a newer schema.

### Manual deploy (escape hatch, or before `production` exists)
```bash
SITE_ADDRESS=api.example.com,api2.example.com AWS_PROFILE=default deploy/aws/deploy.sh   # overrides are optional and remembered
```
Packs your working tree (uncommitted files too), uploads it to the bucket and runs the same `release.sh` on the instance through SSM. It does not touch the `production` branch, and the timer only acts when that branch moves, so a manual deploy is not overwritten until the next promotion. The last 3 releases stay in `/opt/nakama/releases`.

## SMS (phone verification codes)
The API sends texts through Amazon SNS with the instance's AWS role (no keys). **The free plan blocks it**: an AWS policy denies the SMS service, so this needs the Paid plan (AWS Settings, by the project owner). Then, in order:

1. **Let the role publish.** In a stack of its own, so the main stack is untouched:
   ```bash
   ROLE=$(aws cloudformation describe-stack-resource --stack-name nakama --logical-resource-id InstanceRole --query StackResourceDetail.PhysicalResourceId --output text)
   aws cloudformation create-stack --stack-name nakama-sms --capabilities CAPABILITY_IAM \
     --template-body file://deploy/aws/sms-policy.yaml --parameters ParameterKey=RoleName,ParameterValue=$ROLE
   ```
2. **Cap the spend** (account-wide; the policy cannot do this): `aws sns set-sms-attributes --attributes MonthlySpendLimit=5,DefaultSMSType=Transactional`. The default limit is small and raising it needs a support request.
3. **Leave the SMS sandbox.** New accounts may text only phone numbers they verified in the console, until production access is granted (End User Messaging console).
4. **India (TRAI DLT):** register the entity, a sender header and an OTP template with a carrier's DLT portal. Carriers drop unregistered texts to Indian numbers; this is not an AWS rule.
5. **Tell the app** (non-secret settings, one `KEY=value` per line, in a Session Manager shell; the next release picks them up):
   ```bash
   sudo tee -a /opt/nakama/app.env <<'EOF'
   SMS_PROVIDER=sns
   SMS_SENDER_ID=<registered header>
   SMS_DLT_ENTITY_ID=<entity id>
   SMS_DLT_TEMPLATE_ID=<template id>
   SMS_OTP_TEMPLATE=<the approved text, with {code} where the code goes>
   EOF
   ```
   Then promote any commit (or run `deploy/aws/deploy.sh`) so the container restarts with them.

Until all of that is done the routes answer 503 ("Phone verification is not set up yet") and nothing is sent. The API's behaviour and limits are in ONBOARDING 4c.

## Files (photos and 3D models)
The server keeps **no files on its disk**. When `S3_BUCKET` is set (it is on AWS) every upload of a product photo or `.glb` goes to the bucket under `public/items/...` and `/media/public/...` serves it from there (long cache headers, so the CDN or browser asks once). Staff-only files (scans, STL/OBJ, G-code, part models) are uploaded straight to the bucket with short-lived signed URLs and are never served by `/media`. Only the `public/` prefix is ever served; anything else answers 404. With no bucket (development, tests) the app falls back to a local `media` folder. The only state on the server is the database volume.

## Tested in CI
The `aws-rollout` job in `.github/workflows/backend-ci.yml` runs `deploy/aws/ci/rollout-test.sh` on a clean Ubuntu runner with real Docker: the real `release.sh`, cutover, backup and restore-test scripts, with RDS faked by a plain Postgres and S3 by MinIO. It checks, in order: a release on "RDS"; a rehearsal that copies and compares every table without switching; the real cutover (every row copied, API on the local database); the data surviving `docker compose down` and up in its volume; a dump to S3 with old dumps pruned; the restore test; a photo served from S3 with nothing on the server's disk and private objects refused. If a change to `deploy/aws/` breaks any of that, this job fails.

## Database
**Today (until the cutover): RDS.** After the cutover: a separate Postgres 16 container (`db` in `deploy/aws/docker-compose.yml`) with its files in the Docker volume `nakama_pgdata` (on the server's disk; `docker compose down` keeps it, only `down -v` deletes it). It saves about $23 a month (the whole RDS bill) and costs you the managed backups, so it comes with its own:

- **Backups:** `nakama-db-backup` (a systemd timer) dumps the database to `s3://<bucket>/db/` **every 6 hours** and deletes dumps older than 30 days. **Worst case you lose up to 6 hours of data.** Check it with `journalctl -u nakama-db-backup -n 20`; run one now with `sudo systemctl start nakama-db-backup`.
- **Restore test:** `sudo /opt/nakama/current/deploy/aws/db-restore-test.sh` restores the newest dump into a scratch database, checks it has the same tables as the live one, prints the row counts and drops it. **Run it after the first backup, after any change to backups, and about once a month.** A backup you have not restored is a hope, not a backup.
- **Real restore after a disaster** (server lost, disk broken): create the stack again, `docker compose --profile localdb up -d db`, then `pg_restore -U nakama -d nakama --no-owner --clean --if-exists < the-dump` from the newest `db/` file, then a release.
- **Not covered:** a lost or full disk between two backups, and a mistake you notice after 30 days. If 6 hours is too much, take dumps more often (edit `OnCalendar` in `nakama-db-backup.timer`) or turn on continuous WAL archiving.

**The cutover is a deliberate, one-time step, never part of a normal release.** A release uses RDS until the file `/opt/nakama/use-local-db` exists, and only the cutover script creates it. In a Session Manager shell (`sudo -i`):
```bash
/opt/nakama/current/deploy/aws/cutover-to-local-db.sh --rehearse   # copy RDS -> local and compare every table; the API keeps running on RDS
/opt/nakama/current/deploy/aws/cutover-to-local-db.sh              # stop the API, copy, compare, switch, start (a few minutes of downtime)
```
It refuses to switch unless **every table has exactly the same number of rows** on both sides, and puts the API back on RDS if any step fails. RDS is never changed by it. Afterwards stop RDS (`aws rds stop-db-instance`) and delete it a few days later; AWS restarts a stopped database by itself after 7 days, so do not leave it. **To go back to RDS** after a cutover: delete `/opt/nakama/use-local-db` and run a release (anything written since then lives only in the local database: run `sudo systemctl start nakama-db-backup` first).

Day to day: `docker compose --profile localdb ps` and `... logs db` in `/opt/nakama/current/deploy/aws`; a psql shell is `docker compose --profile localdb exec db psql -U nakama nakama`.

## Cost and size
Rough monthly cost at Sydney list prices (check the AWS pricing pages; the real numbers are in the AWS cost report, which lags a day): server `t3.small` about $19, public IP about $3.70, the server's 30 GB disk about $3, secrets and the alarm about $1. **With RDS, add about $23** (database $0.028 an hour plus 20 GB of storage), about $50 a month in all; with the database on the server it is about $27. The credit balance is `aws freetier get-account-plan-state`.

**The server stays `t3.small` (2 GB).** The API (1 worker, about 170 MB), Caddy, Docker and the Postgres container together use about 1.2 GB; `t3.micro` (1 GB) is too small for that. The API runs **1 worker** (`API_WORKERS`) with a 500 MB cap (`API_MEM`), the database a 400 MB cap (`DB_MEM`), and every release makes sure a 2 GB swap file exists (`release.sh`). Raise the three settings in `/opt/nakama/app.env` when there is memory to spare.

**Changing the size of a live stack restarts the server (a few minutes).** Always use a change set, and read it before running it:
```bash
aws cloudformation create-change-set --stack-name nakama --change-set-name resize --use-previous-template \
  --parameters ParameterKey=InstanceType,ParameterValue=t3.medium \
    ParameterKey=VpcId,UsePreviousValue=true ParameterKey=InstanceSubnetId,UsePreviousValue=true \
    ParameterKey=DbSubnetIds,UsePreviousValue=true ParameterKey=DbInstanceClass,UsePreviousValue=true \
    ParameterKey=UbuntuAmi,UsePreviousValue=true ParameterKey=CorsOrigins,UsePreviousValue=true
aws cloudformation describe-change-set --stack-name nakama --change-set-name resize --query 'Changes[].ResourceChange.[LogicalResourceId,Action,Replacement]'
```
**Run it only if `ApiInstance` shows `Replacement: False`.** The Ubuntu image id is looked up again on every update; when Canonical publishes a new image the server would be **replaced**, which loses the server's disk, and with it the database volume (photos are in S3 and are not affected). If it says `True`, delete the change set and resize the instance directly instead (`aws ec2 stop-instances`, `modify-instance-attribute --instance-type`, `start-instances`).

**Night stop** (a separate stack, so it can be paused or removed): the server stops at 00:00 IST and starts at 04:55. Nothing is lost (Docker stops the containers, Postgres shuts down cleanly, the disk and IP stay), but the API and shop data are unreachable in that window and the desktop app shows "server not answering". It saves about $4 a month on the server; the IP and disk cost the same stopped. Use it only once the database is on the server (a database left on RDS is not stopped by it).
```bash
INSTANCE=$(aws cloudformation describe-stacks --stack-name nakama --query "Stacks[0].Outputs[?OutputKey=='InstanceId'].OutputValue" --output text)
aws cloudformation create-stack --stack-name nakama-schedule --capabilities CAPABILITY_IAM \
  --template-body file://deploy/aws/schedule.yaml --parameters ParameterKey=InstanceId,ParameterValue=$INSTANCE
```
Pause it with `State=DISABLED` (`update-stack --use-previous-template`), or run 24 hours again with `delete-stack --stack-name nakama-schedule`. If the server is ever found stopped in the daytime: `aws ec2 start-instances --instance-ids $INSTANCE`.

## First owner account
Interactive, so run it in an SSM session:
```bash
cd /opt/nakama/current/deploy/aws && docker compose exec api python -m app.cli create-owner
```

## Backups
- **Database:** RDS automated backups while it is on RDS (the free plan caps retention at 1 day); after the cutover, the 6-hourly S3 dumps described under "Database".
- **Photos and 3D models:** kept in S3, not on the server (see "Files"). Nothing to back up on the server for them; the bucket is not deleted with the stack.
- Test a restore before you rely on it.

## Not done yet

## Tear down
`aws cloudformation delete-stack --stack-name nakama`. The S3 bucket is kept on purpose (empty and delete it by hand, after downloading the `db/` dumps you want); RDS leaves a final snapshot. **A database on the server's disk is deleted with the server**: run `sudo systemctl start nakama-db-backup` first and keep the dump.
