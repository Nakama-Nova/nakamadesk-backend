# Deploying on AWS

Same shape as [DEPLOY.md](DEPLOY.md), with managed pieces: Caddy and the API run in Docker on one EC2 instance; Postgres is RDS; private files go to S3. Everything is one CloudFormation stack: `deploy/aws/nakama.yaml`.

```
internet -> Caddy (80/443) -> api (uvicorn) -> RDS Postgres 16 (private, SSL)
              EC2 t3.small, Elastic IP          S3 bucket via the instance role
```
No SSH: use SSM (`aws ssm start-session --target <instance-id>`). The database password and `SECRET_KEY` are generated by Secrets Manager and read on the instance at deploy time; they never appear in git, chat or EC2 user-data.

## First time
```bash
aws cloudformation create-stack --stack-name nakama --capabilities CAPABILITY_IAM \
  --template-body file://deploy/aws/nakama.yaml \
  --parameters ParameterKey=VpcId,ParameterValue=<vpc> ParameterKey=InstanceSubnetId,ParameterValue=<subnet> \
               ParameterKey=DbSubnetIds,ParameterValue='"<subnet-a>,<subnet-b>"'
aws cloudformation wait stack-create-complete --stack-name nakama
```
Point a DNS A record at the `ApiEip` address (stack outputs show it), then deploy. Without a domain the stack's `ApiUrl` (an `sslip.io` name) works.

## Branches and releases
Features branch off and merge into `main` through pull requests; CI runs there. **`production` is the release branch.** Promote a tested `main` commit to it and the server deploys it within a minute:

```bash
git push origin main:production      # fast-forward; only the owner can push it
```
How it works: the instance runs a systemd timer (`nakama-pull-deploy`) that asks GitHub for the head of `production`. If it changed and `test` and `docker` are green on that exact commit, it fetches it, builds it, runs `alembic upgrade head`, restarts, and waits for the API to be healthy. If the new API never becomes healthy it goes back to the previous release. A commit whose CI failed is skipped until a new commit arrives. No AWS keys live in GitHub, and nothing in GitHub can reach the server: the server asks GitHub (the repo is public, so no credentials are needed). The free plan's policy blocks GitHub-to-AWS OIDC, which is why it is built this way.

Watch it: `aws ssm start-session --target <instance-id>`, then `journalctl -u nakama-pull-deploy -n 50`.
**Roll back:** push a revert commit to `main`, let CI pass, promote it. Migrations must stay additive (see ONBOARDING), so older code keeps working on a newer schema.

### Manual deploy (escape hatch, or before `production` exists)
```bash
SITE_ADDRESS=api.example.com,api2.example.com AWS_PROFILE=default deploy/aws/deploy.sh   # overrides are optional and remembered
```
Packs your working tree (uncommitted files too), uploads it to the bucket and runs the same `release.sh` on the instance through SSM. It does not touch the `production` branch, and the timer only acts when that branch moves, so a manual deploy is not overwritten until the next promotion. The last 3 releases stay in `/opt/nakama/releases`.

## SMS (phone verification codes)
The API sends texts through Amazon SNS with the instance's AWS role (no keys). **The free plan blocks it**: an AWS policy denies the SMS service, so this needs the Paid plan (AWS Settings, by the project owner). Then, in order:

1. **Let the role publish.** In a stack of its own, so the main stack is untouched:
   ```bash
   ROLE=$(aws cloudformation describe-stack-resource --stack-name nakama --logical-resource-id InstanceRole --query StackResourceDetail.PhysicalResourceId --output text)
   aws cloudformation create-stack --stack-name nakama-sms --capabilities CAPABILITY_IAM \
     --template-body file://deploy/aws/sms-policy.yaml --parameters ParameterKey=RoleName,ParameterValue=$ROLE
   ```
2. **Cap the spend** (account-wide; the policy cannot do this): `aws sns set-sms-attributes --attributes MonthlySpendLimit=5,DefaultSMSType=Transactional`. The default limit is small and raising it needs a support request.
3. **Leave the SMS sandbox.** New accounts may text only phone numbers they verified in the console, until production access is granted (End User Messaging console).
4. **India (TRAI DLT):** register the entity, a sender header and an OTP template with a carrier's DLT portal. Carriers drop unregistered texts to Indian numbers; this is not an AWS rule.
5. **Tell the app** (non-secret settings, one `KEY=value` per line, in a Session Manager shell; the next release picks them up):
   ```bash
   sudo tee -a /opt/nakama/app.env <<'EOF'
   SMS_PROVIDER=sns
   SMS_SENDER_ID=<registered header>
   SMS_DLT_ENTITY_ID=<entity id>
   SMS_DLT_TEMPLATE_ID=<template id>
   SMS_OTP_TEMPLATE=<the approved text, with {code} where the code goes>
   EOF
   ```
   Then promote any commit (or run `deploy/aws/deploy.sh`) so the container restarts with them.

Until all of that is done the routes answer 503 ("Phone verification is not set up yet") and nothing is sent. The API's behaviour and limits are in ONBOARDING 4c.

## First owner account
Interactive, so run it in an SSM session:
```bash
cd /opt/nakama/current/deploy/aws && docker compose exec api python -m app.cli create-owner
```

## Backups
- **Database:** RDS automated backups. The free plan caps retention at 1 day; set `BackupRetentionPeriod` to 7+ after upgrading. A stack delete keeps a final snapshot.
- **Media:** `/srv/nakama/media` on the instance disk is copied to `s3://<bucket>/media-backup/` nightly (cron). Restore by syncing it back.
- Test a restore before you rely on it.

## Cost (ap-southeast-2, rough)
t3.small about $19, db.t3.micro about $16 plus 20 GB storage, public IPv4 about $4: roughly $40-45 a month.

## Not done yet
Multi-AZ database, a load balancer, alarms beyond auto-recover, and cost alerts. Add them when downtime or spend starts to matter.

## Tear down
`aws cloudformation delete-stack --stack-name nakama`. The S3 bucket is kept on purpose (empty and delete it by hand); the database leaves a final snapshot.
